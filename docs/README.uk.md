Chibi созданий для моменту, коли ви розумієте: вам потрібен не просто «AI-інструмент». Вам потрібен **партнер**, здатний координувати моделі, виконувати роботу у фоні та інтегруватися з вашими системами — без постійного контролю промптів.

**Chibi** — асинхронний self-hosted **цифровий компаньйон у Telegram**, який оркеструє AI-провайдерів та інструменти, щоб досягати результатів: змін у коді, аналітичних узагальнень, генерації медіа й операційних задач.

---

## Чому Chibi

- **Один інтерфейс (Telegram).** Мобільний, десктопний і веб — завжди з вами.
- **Незалежність від провайдера.** Використовуйте найкращу модель для кожної задачі без прив’язки до вендора.
- **Автономне виконання.** Субагенти працюють паралельно, а довгі задачі виконуються у фоні.
- **Підключення інструментів.** Файлова система + термінал + інтеграції MCP (GitHub, браузер, БД тощо).
- **Self-hosted.** Ваші дані, ваші ключі, ваші правила.

## 🚀 Швидкий старт (pip)

Встановіть Chibi через pip та запустіть як додаток командного рядка:

```bash
# Встановлення пакета
pip install chibi-bot

# Налаштування агента (додайте API-ключі, змініть налаштування тощо)
chibi config

# Запуск бота
chibi start
```

Бот працюватиме як фонова служба. Використовуйте CLI-команди для керування.



| Команда | Опис |
|---------|-------------|
| `chibi start` | Запуск бота у фоні |
| `chibi stop` | Зупинка працюючого бота |
| `chibi restart` | Перезапуск бота |
| `chibi config` | Створення або редагування конфігурації |
| `chibi logs` | Перегляд логів бота |

## Локальні клієнтські інтерфейси

Chibi може обслуговувати локальні клієнти через версійований локальний протокол JSONL:

```bash
chibi stdio --tui
chibi stdio --vscode
chibi stdio --pycharm
chibi stdio --neovim
```

Команда призначена для запуску клієнтським інтерфейсом, а не для інтерактивного використання. Chibi є власником протоколу `v1` і підтримує сумісні клієнти, які узгоджують ту саму версію. Процес stdio записує кадри протоколу лише в stdout, а діагностичні повідомлення — у stderr. Наявні механізми Chibi для команд, інструментів, дозволів і модерації лишаються визначальними; клієнт не додає власного шару політик для інструментів.

## 🚀 Швидкий старт (Docker)

Створіть `docker-compose.yml`:

```yaml
version: '3.8'

services:
  chibi:
    image: pysergio/chibi:latest
    restart: unless-stopped
    environment:
      TELEGRAM_BOT_TOKEN: ${TELEGRAM_BOT_TOKEN}  # Обов’язково
      OPENAI_API_KEY: ${OPENAI_API_KEY}          # Або будь-який інший провайдер
      # Додайте інші API-ключі за потреби
    volumes:
      - chibi_data:/app/data

volumes:
  chibi_data: {}
```

1) Отримайте токен бота у [@BotFather](https://t.me/BotFather)

2) Додайте секрети в `.env`

3) Запустіть:

```bash
docker-compose up -d
```

Далі:
- **Гайд з інсталяції:** https://chibi.bot/installation
- **Довідник з конфігурації:** https://chibi.bot/configuration

## Спробуйте це в перші 5 хвилин

Скопіюйте та вставте ці запити в Telegram після деплою.

1) **Планування + виконання**
> Постав мені 3 запитання, щоб уточнити мою ціль, потім запропонуй план і виконай крок 1.

2) **Паралельна робота (субагенти)**
> Створи 3 субагенти: один - щоб дослідити варіанти, другий - щоб підготувати рекомендацію, третій - щоб перелічити ризики. Поверни одне узгоджене рішення.

3) **Режим агента (інструменти)**
> Переглянь файли проєкту та підсумуй, що робить цей репозиторій. Потім запропонуй 5 покращень і відкрий чекліст.

4) **Фонова задача**
> Запусти фонову задачу: збери джерела про X і підготуй синтез за 30 хвилин. Тримай мене в курсі.

## Чим Chibi відрізняється від інших

### 🎭 Оркестрація кількох провайдерів
Chibi може зберігати контекст, перемикаючись між провайдерами в межах одного діалогу, або обирати найкращу модель для кожного кроку - балансуючи **вартість**, **можливості** та **швидкість**.

### 🤖 Автономні можливості агента
- **Рекурсивне делегування:** створюйте субагентів, які можуть створювати власних субагентів
- **Фонова обробка:** довгі задачі виконуються асинхронно
- **Доступ до файлової системи:** читання/запис/пошук/організація файлів
- **Виконання команд у терміналі:** запуск команд із LLM-модерованою безпекою
- **Постійна пам’ять:** історія розмов зберігається між перезапусками з керуванням контекстом/підсумовуванням
- **Навички:** багаторазові модулі інструкцій, які агент може за запитом завантажити до системного промпту (`load_builtin_skill`)

### 🔌 Розширюваність через MCP (Model Context Protocol)
Підключайте Chibi до зовнішніх інструментів і сервісів (або створюйте власні):

- GitHub (PR, issues, code review)
- Автоматизація браузера
- Docker / хмарні сервіси
- Бази даних
- Креативні інструменти (Blender, Figma)

Якщо інструмент можна реалізувати через MCP, Chibi зможе навчитися ним користуватися.

### 🎨 Генерація контенту
- **Зображення:** Nano Banana, Imagen, Qwen, Wan, GPT Image, Grok Imagine, GLM Image
- **Музика:** Suno (включно з custom mode: стиль/лірика/вокал)
- **Голос:** транскрипція + text-to-speech (ElevenLabs, OpenAI, MiniMax)

## Приватність, контроль і безпека

- **Self-hosted:** ваші дані залишаються у вашій інфраструктурі
- **Public Mode:** користувачі можуть підключати власні API-ключі (спільний майстер-ключ не потрібен)
- **Контроль доступу:** білий список (whitelist) користувачів/груп/моделей
- **Варіанти зберігання:** локальні томи, Redis або DynamoDB
- **Безпека інструментів:** інструменти агента налаштовуються; виконання в терміналі модеруються та можуть бути обмежені

### `MAX_HISTORY_TOKENS` — поріг підсумовування контексту (зміна значення за замовчуванням, що порушує сумісність)

`MAX_HISTORY_TOKENS` — поріг, після досягнення якого Chibi автоматично підсумовує розмову, щоб контекст лишався керованим. Його **семантика змінилася**: тепер значення порівнюється з **реальною кількістю токенів промпту, яку повідомляє провайдер** (увесь вихідний запит: системний промпт + активовані навички + схеми інструментів + аргументи викликів інструментів + структурні накладні витрати на повідомлення + вміст розмови), а не зі старою евристикою, що вимірювала лише `content` + `role` розмови. Для однакової розмови реальна величина приблизно у **4,8 раза більша** за попередню оцінку (виміряний розподіл наведено в `fix_context_size/context_size_accounting_analysis.md`).

- **Нова база за замовчуванням:** `64000` → `100000`. Нове значення захищає найменше з поширених вікон контексту (128k токенів): `100000` — близько 78 % вікна в 128k (підсумовування запускається *до* переповнення моделі з 128k) і близько 50 % вікна в 200k (із комфортним запасом). Старе `64000` було оцінкою лише історії та не досягалося до реального переповнення, оскільки воно приблизно вдвічі недооцінює кирилицю й виключає сталі накладні витрати на хід (системний промпт ~3,7k, схеми інструментів ~6,8k, активовані навички ~5,9k, `user_info` ~0,75–3k) — тому модель із вікном 128k переповнювалася приблизно на 128k реальних токенах, поки евристика все ще показувала значно менше 64k.
- **Міграція:** якщо ви явно задали `MAX_HISTORY_TOKENS` в `.env`, попереднє значення було налаштоване на стару оцінку лише історії, а тепер порівнюється з правдивою величиною, яка для тієї самої розмови приблизно у 4,8 раза більша. Переналаштуйте його на масштаб **близько 100k** (наприклад, `64000` → `100000`), щоб підсумовування відбувалося до переповнення вікна контексту вашої найменшої моделі, а не після. Якщо ви нічого не задавали, нове значення за замовчуванням застосовується автоматично.
- Резервний механізм холодного старту (перший хід після перезапуску процесу, коли дані провайдера ще не кешовані) як і раніше використовує стару евристику, тому підсумовування продовжує працювати.

### `REACTIVE_CONTEXT_RECOVERY` — одноразова повторна спроба після переповнення контексту

`REACTIVE_CONTEXT_RECOVERY` (за замовчуванням: `true`) — реактивний захист, що доповнює проактивний поріг `MAX_HISTORY_TOKENS`. Коли провайдер відхиляє запит із типізованою помилкою `context_length_exceeded`, Chibi автоматично підсумовує історію та повторює хід **рівно один раз**. У разі успіху користувач отримує звичайну відповідь (із коротким повідомленням, що контекст було стиснено). Якщо повторна спроба знову переповнює контекст або відновлення з будь-якої причини не вдається, хід переходить до наявного шляху з вибаченням — цикл підсумовування й повтору ніколи не запускається більше одного разу для початкового ходу. Установіть `false`, щоб вимкнути реактивне відновлення та лишити попередню поведінку (лог + вибачення, без повтору).

### Робочий каталог прив’язаний до треду (`WORKING_DIR`)

Робочий каталог агента — який використовується для команд термінала та повідомляється моделі як її поточний CWD — прив’язаний до треду, як і вибрана LLM-модель.

- **За замовчуванням:** береться з налаштування `WORKING_DIR` (за замовчуванням `~/chibi`) через застаріле користувацьке значення; нові розгортання успадковують налаштування напряму.
- **Перевизначення для треду:** будь-який тред/розмова може ізольовано перевизначити робочий каталог за допомогою інструмента агента `set_working_dir` (лише з ініціативи LLM — slash-команди немає; інструмент доступний за ввімкненого `FILESYSTEM_ACCESS`). Це дозволяє двом агентам у різних тредах одночасно працювати з різними проєктами, не заважаючи один одному.
- **Порядок визначення:** перевизначення треду → застарілий користувацький каталог → налаштування `WORKING_DIR`.
- **Нормалізація шляху:** задані значення під час збереження розгортаються в абсолютні (`~/x` стає `/abs/x`); незмінені значення за замовчуванням зберігають початковий вигляд.
- **Субагенти**, створені в треді, використовують його робочий каталог — той самий чинний шлях передається до їхніх системних промптів і викликів інструментів.
- Перевизначення **зберігаються під час клонування треду**: `/new_thread_with_current_context` переносить робочий каталог разом із повідомленнями та налаштуваннями моделі.
